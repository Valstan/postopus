# 📘 Postopus — Документация проекта для AI-разработчиков

## 🎯 Назначение проекта
**Postopus** — автоматизированная система парсинга, фильтрации и постинга контента из ВКонтакте для сети региональных новостных пабликов.

---

## 🏗 Архитектура проекта

### Структура директорий
```
/workspace/
├── bin/                      # Основные модули
│   ├── ai/                   # AI-модули (OCR, сортировка)
│   ├── control/              # Контроллеры сценариев (parser, repost_*, sosed и др.)
│   ├── rw/                   # Чтение/запись (VK API, MongoDB, файлы)
│   ├── sort/                 # Сортировка постов (по дате, фото, видео)
│   └── utils/                # Утилиты (текст, изображения, таблицы)
├── service/                  # Сервисные скрипты (аналитика, SEO, статистика)
├── config.py                 # Конфигурация (токены, настройки сессий)
├── start.py                  # Точка входа
├── start_paket.py            # Пакетный запуск по регионам
└── requirements.txt          # Зависимости
```

### Ключевые компоненты
| Модуль | Описание |
|--------|----------|
| `bin/control/parser.py` | Парсинг постов из VK, фильтрация по дубликатам, blacklist, региональным словам |
| `bin/rw/posting_post.py` | Публикация дайджестов в целевые группы VK |
| `bin/control/control.py` | Диспетчер сценариев (novost, reklama, addons, repost_*) |
| `bin/utils/driver_tables.py` | Работа с таблицами состояний (MongoDB) |

## 🔐 Безопасность и секреты

### ⚠️ КРИТИЧЕСКИ ВАЖНО: VK токены
1. **Хранение токенов**: Все секреты должны храниться **ТОЛЬКО** в `.env` файле (не в `config.py`!)
2. **Оптимизация API-запросов**: 
   - Избегать избыточных вызовов VK API
   - Использовать кэширование где возможно
   - Соблюдать rate limits VK (~3 запроса/сек на токен)
   - При ошибках 429 делать exponential backoff
3. **Риск блокировки**: Превышение лимитов → блокировка токена → остановка постинга
4. **Разделение токенов**:
   - `VK_TOKEN_VALSTAN` — основной (чтение + постинг)
   - `VK_TOKEN_VITA` — только чтение
   - Использовать рандомизацию при выборе токена

### Пример `.env` (создать, не коммитить!)
```env
VK_TOKEN_VALSTAN=vk1.a....
VK_TOKEN_VITA=vk1.a....
MONGO_CLIENT=mongodb+srv://...
TELEGA_TOKEN_VALSTANBOT=...
YANDEX_DISK_TOKEN=...
```

### Загрузка из env
```python
from dotenv import load_dotenv
import os
load_dotenv()
token = os.getenv('VK_TOKEN_VALSTAN')
```

## 📝 Типизация и валидация

### Требования к коду
1. **Type hints**: Все функции должны иметь аннотации типов
   ```python
   def parser(stat_mode: bool = False) -> list[dict] | dict:
       ...
   ```
2. **Валидация входных данных**: Проверка типов и значений параметров
3. **Data classes**: Использовать `@dataclass` для структур данных
4. **Pydantic**: Для сложной валидации конфигов и моделей

### Пример
```python
from typing import Optional
from dataclasses import dataclass

@dataclass
class Post:
    id: int
    text: str
    owner_id: int
    views: Optional[int] = None
    
def process_post(post: Post) -> bool:
    if not isinstance(post.id, int):
        raise TypeError("post.id must be int")
    ...
```

## 🔐 Настройка SSH-доступа к GitHub (ПЕРВЫЙ ШАГ каждой сессии)

### ⚠️ КРИТИЧЕСКИ ВАЖНО: Начинать каждую сессию с создания SSH-ключа

**Перед любыми действиями с Git AI-разработчик ДОЛЖЕН:**

1. **Сгенерировать новый SSH-ключ Ed25519 БЕЗ парольной фразы:**
   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_postopus -N "" -C "postopus-bot@github"
   ```
   > ⚠️ Параметр `-N ""` критически важен — он создаёт ключ без passphrase для автоматизированной работы

2. **Показать пользователю публичный ключ для добавления на GitHub:**
   ```bash
   cat ~/.ssh/id_ed25519_postopus.pub
   ```
   
   **Формат сообщения пользователю:**
   ```
   ## 🔑 Ваш публичный ключ для добавления на GitHub:

   [содержимое файла .pub]

   ### Инструкция по добавлению ключа:
   1. Перейдите в настройки вашего аккаунта GitHub: https://github.com/settings/keys
   2. Нажмите "New SSH key"
   3. В поле Title введите: postopus-bot
   4. В поле Key вставьте вышеуказанный публичный ключ целиком
   5. Убедитесь, что выбран тип ключа "Authentication Key"
   6. Нажмите "Add SSH key"
   
   После добавления ключа подтвердите это — я продолжу синхронизацию.
   ```

3. **Настроить SSH для использования нового ключа:**
   ```bash
   # Создать или обновить конфиг SSH
   echo -e "Host github.com\n  HostName github.com\n  User git\n  IdentityFile ~/.ssh/id_ed25519_postopus\n  IdentitiesOnly yes" >> ~/.ssh/config
   chmod 600 ~/.ssh/config
   ```

4. **Проверить подключение к GitHub:**
   ```bash
   ssh -T git@github.com
   ```
   Ожидаемый ответ: `Hi Valstan! You've successfully authenticated...`

## 🔄 Управление историей разработки (CRITICAL)

### Обязательное ведение журнала изменений

**После каждого значимого изменения в проекте AI-разработчик ОБЯЗАН:**

1. **Зафиксировать изменения** в файле `/workspace/DEV_HISTORY.md`:
   - Создание новых модулей/сервисов
   - Изменение архитектуры или структуры проекта
   - Модификация ключевой логики работы
   - Обновление зависимостей или конфигурации
   - Изменение контрактов API или форматов данных

2. **Формат записи в DEV_HISTORY.md**:
```markdown
## [Дата] - [Краткое описание изменения]

### Что изменено:
- [Список конкретных изменений]

### Затронутые файлы:
- `path/to/file1.py` - описание изменения
- `path/to/file2.py` - описание изменения

### Причина изменения:
[Обоснование архитектурного решения]

### Влияние на другие модули:
[Какие компоненты затронуты, требуется ли миграция]

### Обратная совместимость:
[Да/Нет/Частично - если нет, описать breaking changes]
```

3. **Актуализация характеристик проекта**:
   - После внесения изменений обновить соответствующие разделы в `AI_DEV_GUIDE.md`
   - Удалить или пометить как `[УСТАРЕЛО]` информацию, которая больше не актуальна
   - Добавить новые разделы при появлении новых модулей/функций

4. **Очистка устаревшей информации**:
   - При удалении модулей — удалить их описание из документации
   - При рефакторинге — переписать устаревшие разделы
   - Не допускать накопления противоречивой информации
   - Регулярно проводить ревизию документации (каждые 5-10 значимых изменений)

### Почему это критически важно:

⚠️ **Без актуальной истории разработки:**
- Нейросеть в новых сессиях будет использовать устаревшие сведения
- Возможны регрессии и возврат к уже исправленным проблемам
- Деградация архитектуры из-за противоречивых решений
- Потеря контекста важных архитектурных решений

✅ **Правильное ведение истории обеспечивает:**
- Сохранение контекста между сессиями разработки
- Быстрое понимание текущего состояния проекта
- Предотвращение повторения ошибок
- Эволюционное развитие архитектуры без деградации

### Пример ведения истории:

```markdown
## 2025-01-15 - Рефакторинг сервиса VK API

### Что изменено:
- Выделен отдельный модуль `services/vk_rate_limiter.py` для контроля запросов
- Добавлен кэширующий слой для часто запрашиваемых данных
- Изменён интерфейс `VKAPIClient` - теперь требует параметр `rate_limit_policy`

### Затронутые файлы:
- `services/vk_client.py` - добавлен rate limiter
- `services/vk_rate_limiter.py` - новый файл
- `config/settings.py` - добавлены настройки лимитов

### Причина изменения:
Предотвращение блокировки токенов VK из-за превышения лимитов API

### Влияние на другие модули:
Все модули, использующие `VKAPIClient`, должны передать политику лимитирования

### Обратная совместимость:
Нет - требуется обновить все вызовы клиента
```
